# WebsFlow 生态 · 面向未来的平台规划

> 两条原则（本规划的出发点）
> **P1 一切皆 API** —— 每个系统都能被其它系统调用，能力互为输入，形成双向赋能网络。
> **P2 一切可自进化** —— 每个系统都具备「感知 → 决策 → 执行 → 验证」闭环，且闭环可度量、可干预、可回滚。

---

## 一、现状:已经具备的"可赋能资产"

| 系统 | 已有能力 | 已暴露接口 | 可被别人用什么 |
|---|---|---|---|
| **WebsFlow**(本系统) | 造页/改稿/变体/主题令牌/千人千面/自动化/增长 Agent(多目标·人审·风控·经验学习)/嵌入式埋点 | `POST /api/tools/call`(14 工具) · `GET /api/tools/manifest` · MCP stdio · 托管页 `/p/<token>` | 一句话造页、结构化改稿、发布、读转化数据、跑 A/B、提案审批 |
| **OpenFlow** | CDP 事件采集、待办/CRM、身份与社区、内容域 | `/api/cdp.php`、待办 API、事件查询 | 全站身份、流量与渠道、线索承接与质量反馈 |
| **PayFlow** | 收款、券校验、订单、结算与提现 | 券校验(`automation/coupon` 已代理)、订单/结算 API、Webhook(已接 `webhooks/payflow`) | 支付成功/退款事件、券与价格校验、结算真源 |
| **UserLoop / inflow**(反代在 :8600 / :8400) | 用户回路 / 流量侧能力 | 各自 HTTP 接口 | 待纳入统一能力注册(见缺口 G3) |

**已经打通的样板(证明模式可行)**:
1. 表单线索 → 写 OpenFlow 待办(WebsFlow → OpenFlow)✅
2. 券校验 → 透传 PayFlow(`/api/automation/coupon`)✅
3. 支付结果 → PayFlow Webhook 回灌 WebsFlow 对账 ✅
4. 外部 Agent → 工具 API 造页/跑实验 ✅

## 二、赋能图谱(双向流动)

```
        ┌──────────────────── 身份与流量 ────────────────────┐
        │                                                    ▼
   OpenFlow ──(渠道/UTM/人群/线索质量)──►  WebsFlow ──(落地页/分群事件/实验结论)──► OpenFlow
        ▲                                     │                                      │
        │                                     │ 转化与订单                            │ 待办/CRM
        │                                     ▼                                      ▼
   PayFlow ◄──(转化事件/归因)───────────  WebsFlow ──(收款页/券)──────────────► PayFlow
```

| 方向 | 载荷(建议字段) | 用途 |
|---|---|---|
| OpenFlow → WebsFlow | `channel, utm, audience, lead_quality(0-1), identity(vid/uid)` | 让落地页知道"谁来了、来自哪、值多少钱" → 分群与 Agent 目标更准 |
| WebsFlow → OpenFlow | `lead, form_submit, segment_seen, experiment_result` | 线索承接、人群沉淀、实验结论进客户档案 |
| PayFlow → WebsFlow | `order_paid, refund, coupon_valid, plan` | 收款页转化回灌、券有效性、套餐联动 |
| WebsFlow → PayFlow | `cta_click, form_submit(带 goal)` | 收款页归因、佣金计算输入 |

**关键约定**(避免互相打架):
- **单一真源**:线索客户档案在 OpenFlow;支付与结算在 PayFlow;页面与投放转化在 WebsFlow。跨系统只传"事实事件",不传"可变状态"。
- **幂等**:所有跨系统事件带 `event_id`,接收方按 id 去重;重试安全。
- **不回写对方真源**:WebsFlow 不直接改 OpenFlow 的线索状态,只投递事件与待办。

## 三、自进化机制:每个系统都跑的同一套回路

```
感知(Sense) → 决策(Decide) → 执行(Act) → 验证(Verify) → 沉淀(Lesson) ─┐
      ▲                                                                  │
      └─────────────────────── 下一轮用上经验 ─────────────────────────┘
```

| 系统 | 感知 | 决策 | 执行 | 验证 | 已沉淀经验 |
|---|---|---|---|---|---|
| WebsFlow | CDP 事件 + A/B 样本 + 分群/来源 | 增长 Agent(LLM 提假设)+ 阈值告警 | 自动化引擎 / 工具 API / 发布变体 | 两比例 z 检验 + 显著性 | `growth_runs.categories/theme` + 跨项目胜率 + 人工驳回规避 |
| OpenFlow | CDP 全站事件 + 内容表现 | 编辑策略 / 人群运营 | 内容发布 / 待办流转 | 内容指标对比 | 待补(见 G4) |
| PayFlow | 订单/退款/结算 | 价格与券策略 | 结算 / 提现 | 对账差异 | 对账报告已入库 |

**进化的度量**(建议纳入统一看板):
- 回路周期:从"发现问题"到"验证结论"的平均时长(WebsFlow 已可算:轮次 `started_at → concluded_at`)
- 胜率曲线:每 10 轮的 `winner=B` 占比是否上升(经验学习是否真的有效)
- 自动化覆盖率:由系统自己执行的动作 / 总动作
- 干预率:人工驳回 / 提案总数(过高说明 Agent 判断差,过低说明人没在看)

## 四、缺口清单(要成为"互相赋能 + 自我进化"的平台还缺什么)

| 编号 | 缺口 | 为什么要 | 建议形态 |
|---|---|---|---|
| G1 | **事件回传总线**(外部 → WebsFlow) | 现在只有页面自采;OpenFlow/PayFlow 的事实进不来,Agent 看不到"线索质量" | `POST /api/ingest`(API key + 幂等 event_id),落 `events` 并参与分群/实验 |
| G2 | **身份打通** | `vid`(访客) ↔ `uid`(登录) ↔ `payflow_ref`(支付) 现在各自为政 | 统一 `identity` 表 + 解析规则;跨系统用同一 `uid` 贯通 |
| G3 | **能力注册与发现** | 系统变多后,Agent 需要"问平台谁能做什么" | 各系统注册 `/capabilities`(名称/参数/计费/限流),聚合为平台能力目录 |
| G4 | **经验沉淀标准化** | 目前只有 WebsFlow 有经验库 | 统一 `lessons` 契约(场景/动作/结果/样本量),各系统共用一份"平台经验" |
| G5 | **跨系统审计与配额** | 平台化后调用方是第三方 Agent | 现有 API key 加 `scope`(read/write/growth)+ 调用配额 + 审计日志 |
| G6 | **契约版本化** | 工具会被外部依赖 | manifest 加 `version`/`deprecated`,变更走兼容策略 |
| G7 | **端到端观测** | 排障与优化需要全链路 | 一次投放的 trace:曝光→点击→线索→订单→结算,用统一 `trace_id` |

## 五、路线图(三阶段,含验收指标)

### 阶段 1 · 打通(1–2 周)
做 G1 + G2 + G5:事件回传、身份打通、密钥分级与审计。
**验收**:OpenFlow 能用 api key 把"线索质量"回传 WebsFlow;WebsFlow 的 Agent 能在假设里引用该质量分;一次跨系统调用可在审计里查到。

### 阶段 2 · 自驱动(约 1 个月)
做 G3 + G4 + G6:能力目录、统一经验契约、契约版本化;并把 WebsFlow 增长 Agent 的"目标"扩展为可被外部指定(如"以 OpenFlow 的线索质量为优化目标")。
**验收**:给出目标(`提升高质量线索占比`)后,系统自选落地页改动并跑完实验;经验库里能查到跨系统的胜率归因。

### 阶段 3 · 自治(一个季度)
**已落地(4.32.x)**:G7 轨迹 + 目标驱动编排 + **跨系统动作编排**(决策 → `capabilities` 调用,默认人审,`cross_actions` 队列)已全部完成。

原计划:做 G7 + 目标驱动的编排:把"操作"升级为"意图"——给平台一个 KPI(如"线索成本下降 20%"),由 Agent 自行组合:改落地页 → 调投放(OpenFlow)→ 验券/收款(PayFlow)→ 复盘 → 再迭代。
**验收**:连续 3 个 KPI 周期无需人工起草方案(人只审批),且每轮结论可解释、可回滚。

## 六、边界与硬约束(不允许 AI 越界)
- **钱与价格**:AI 不得自行改价、发券额度、发起提现;只能"建议 + 人审"(PayFlow 为真源)。
- **对外发布**:未经人审不得把新变体推到生产(已有 `approval_mode`)。
- **数据归属**:线索与客户档案归 OpenFlow;支付归 PayFlow;页面归 WebsFlow;跨系统只投递事实。
- **风控优先于增长**:风险闸门(零转化/流量骤降/连续不显著)优先于增长动作;命中即暂停并通知。
- **可回滚**:每一轮改动均有快照/版本,可一键回滚(已有)。

## 七、现在就能做的三件事
1. **G1 事件回传**(半天):`POST /api/ingest` + 幂等;立刻让 OpenFlow 的线索质量进入 WebsFlow 决策。
2. **G5 密钥分级与审计**(半天):`scope` + 审计日志;平台化后这是安全底线。
3. **G4 统一经验契约**(1 天):把 WebsFlow 的 `growth_runs` 经验结构抽成通用契约,供其它系统复用。

*原则不变、边界清晰、回路可度量 —— 这样"互相赋能"不会变成互相耦合,"自我进化"也不会失控。*
